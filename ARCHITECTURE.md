# ARES Protocol Architecture Document
## Overview

The ARES protocol was built around one idea - nothing touches the treasury directly. Every action has to go through a proposal, get confirmed, wait out a delay, and then execute. The system is split into four folders: modules, libraries, interface, and core. Each folder has a specific job and not overlap.

## System Architecture
The system works in layers. A user action starts at the core layer where the cryptographic authorization layer verifies the signature, checks the nonce, and makes sure the signature has not been used before. Oncce that passes, the action moves into the modules. The modules has its own state, the mappings, the proposal structs, the transaction queue. They use the libraries to validate inputs and compute the hashes, and they use the interfaces to talk to external contracts like the token and the treasury. The proposal module handles the full proposal lifecycle. The time DelayedExecutionEjgine sits bewteen approved proposals andthe treasury, making ure nothing executes  without waiting out the delay. AREES handles contributpr rewards seperately using a merkle tree of thousands of recipients without storing all of them on chain.
