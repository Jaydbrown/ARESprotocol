# ARES Protocol Architecture Document
## Overview

The ARES protocol was built around one idea - nothing touches the treasury directly. Every action has to go through a proposal, get confirmed, wait out a delay, and then execute. The system is split into four folders: modules, libraries, interface, and core. Each folder has a specific job and not overlap.

## System Architecture
The system works in layers. A user action starts at the core layer where the cryptographic authorization layer verifies the signature, checks the nonce, and makes sure the signature has not been used before. Oncce that passes, the action moves into the modules. The modules has its own state, the mappings, the proposal structs, the transaction queue. They use the libraries to validate inputs and compute the hashes, and they use the interfaces to talk to external contracts like the token and the treasury. The proposal module handles the full proposal lifecycle. The time DelayedExecutionEjgine sits bewteen approved proposals andthe treasury, making ure nothing executes  without waiting out the delay. AREES handles contributpr rewards seperately using a merkle tree of thousands of recipients without storing all of them on chain.

## Module Seperation
The reason libraries are seperate from modules is that libraries have no state, ProposeAssetTransaction validates the inputs for  transfer, call, and upgrade but it does not execute anything and it does not store anything. The module calls the library first, and if the validyion passes, the module handles the storage and the lifecycle. This keeps the logic clean - if you need to change the validation rukes you cahnge the library nd you do not change the modules. Same thing with the MerkleLib. It builds the leaf, verifies the proof, recovers the signer. It does not know about the root or claimed the mapping those live in ARES. The library just does the computation and returns the result. MultiSigLib works the same way - it takes the storage pointer from the module, operates on it, and hands control back.

## Trust Assumptions

Admin is trusted. if admin is compromised the attacker can queue the transactions and commit proposals. the three proposer confirmation requirement slows this down because admin alone cannot move a proposal to Ready. But a patient attacker who controls admin can still get proposals after executed after the delay. The multisig in ARES reduces the single point of failure for  root updates. No single owner can update the root alone - the threshold. has to be met. but proposalsModule and TimeDelayedExecutionENgine are still singke admin controlled.
